## 领域、所有权与生命周期

保留现有实体、数据库事实源和调度器。

1. Task 持有目标、负责人、版本与 contract；Submission / Review 对应确切产物与证据，作者不得自审。
2. 人工结果确认与逐项技术审核明确区分。在 human Gate 增加可选结果确认语义，只有新流程明确选择时启用；缺省保持旧严格审核。Agent / code Gate 仍要求逐项证据。结果确认不能填造用户独立做过技术检查。
3. Selection 保留固定样例、模型、预算、三方执行和接收验证，新增独立审核安排并复用 Gate 调度。已有人工 Selection 不自动改约定。Agent 可在授权范围内准备提案与评测，不能获得 owner 发布权限。
4. 应用改进必须指定 Channel、候选及影响范围，通过 TeamVersion 保存目标组合。不能把更新 agents 全局配置描述成只改一支团队；相关 owner 批准仍需满足。沿用现有快照边界：已经创建的 Run（包括远端排队 Run）保持原快照；尚未生成 Run 的 Inbox 待办在领取时使用当时获准的版本，不复制运行凭据或冻结过时的上下文。
5. WorkMark / HeldDraft / Wait 由原负责 Agent 和 Server 管理。已读、Run 结束、放弃草稿均不等于完成承诺。
6. 跨 owner 合作由双方确认；Agent 只起草。撤回阻止后续使用，历史保留。

## 数据流与 API

### 交办、补充、交付

原频道或线程交办 → Leader 读取来源、整理要求、安排审核 → 创建或原地接住 Task → Worker 执行 → 提交成果及 Handoff → Reviewer 检查并返工 → 满足约定后交付或进入明确人工决定。

明确 Task 线程内的补充，Server 在发送事务中绑定同一上下文唯一可识别的活动工作，复用 freshness 与队列合并。多项工作不能区分时不擅自绑定，交 Agent 澄清。自动绑定发生竞态时仍保存普通补充消息，不能丢失用户输入。

交付弹窗先展示当前成果、整体结论和剩余问题。要求、历史、成本、证据只读展开；验收安排按原权限低频编辑。新的人工结果确认保存真实接受意见；严格人工审核保持原要求。

### 等待与内部承诺

Agent 读取尚欠工作并登记条件 → 结束当前 Run、处理其他工作 → Server 等待时间或依赖就绪 → 恢复同一 Task。仅当 signal 需要本人输入时，任务旁出现具体操作并复用原等待弹窗。确认人、证据、来源及幂等由 Server 校验。

资料摘要展示当前工作和阻塞；队列、承诺与草稿进入工作记录。原 CLI 保留，提示词要求在实际完成、取消或收到更正时更新；恢复时重读承诺，不能隐藏后永久遗留。禁止自我唤醒循环和无意义轮询。

### 改进、对照与应用

真实反馈 → Agent 准备 Revision 与 Selection → 校验权限、Computer、预算 → 三方实际执行 → 独立 Reviewer 检查确切提交 → 展示问题、证据、代价及影响范围 → owner 采用并应用或暂不采用 → Server 保存选择与目标团队版本 → 后续 Run 使用获准快照。

CLI / daemon 补充 Selection 查询与发起代理，仍使用当前 Run 身份。不能无条件将 Agent ID 换成 owner ID 绕过授权。复用现有 HTTP、服务与持久表，不另建评测调度器。

一键采用对应一个明确用户决定，底层选择和应用仍分别有记录。失败可重试且不能提前显示成功；目标团队或旧基线变化时拒绝过期提案。恢复只影响后续工作，外部操作和原历史不倒退。

## 持久化、迁移与兼容

沿用 PostgreSQL 事务、幂等键、版本检查及预算账本。contract / selection plan / lockfile 的向后兼容字段优先放入已有 JSON；只有需要独立约束的新事实才增加迁移。

不回填猜测的历史意图。旧 human Gate 缺省严格，旧 Selection 保持人工安排，旧等待与发布记录可读。现有全局发布兼容接口不能被“应用到当前团队”误调用。原模型、Skill、接收策略、自动任务 API 保留。

所有共享调用方一起更新，包括频道、DM、Inbox、成员侧栏和任务看板；保留业务任务、Thinking、Session、自动组队身份与记忆。私有数据可见性、Computer 权限及双方批准不能因减少按钮而扩大。

## 自动评测的具体执行约束

新自动评测在原三份执行副本之外，固定一份独立审核副本，来自同 owner 的另一位成员；审核者不能是被评估成员或接收方。第四份副本复用 trial 的版本固定、预算与使用量账本，原三方输入和接收规则不变。新增 reviewer arm 的数据库约束迁移；旧人工评测仍保留三份副本和原审核人。新 Agent 发起评测必须提供独立审核人；身份由自己的有效 Agent 权限核实后解析 owner，只允许给自己提案，不能代替 owner 决定。

审核通过已有 Task review 调度器执行，只允许审核这轮 Selection 的当前提交。审核配置改变、活动运行、未知用量或超预算时都不能采用。审核任务仍有原三次尝试限制。评测源频道和目标团队版本另外记录，应用检查同一基线，避免将全局配置误用于团队内对照。

## 自然交办的初始验收约定

Leader 创建新子任务时，沿用现有 `task create --contract-file` 一并给出 requirements 和独立 Gate。已有用户消息需要原地接成 Task 时，扩展原 `task claim --message-id --contract-file`，在同一事务内保存初始约定；不另建 Task、不改变来源作者与所有权。对于 Agent 领取人类消息，初始 Gate 只能由来源人确认结果，不能偷偷把用户的接受权交给 Agent 或运行检查命令。团队技术验证由独立子任务完成，实际证据写入原任务交付。

已有 Task（无论是否设置过约定）不得通过 claim 重写规则；重复同一约定幂等，不同约定冲突。显式改约定继续走原 creator 权限与 Task 版本检查。未提供 contract 的旧领取请求完全兼容。初始 contract 非法、审核者自审、来源不合适或领取竞争失败时，整个转换回滚。

此规则经现有 REST → daemon 代理 → CLI → messageTask → PostgreSQL 原子转换路径落地，前端不增加新表单。真实 E2E 从原对话发出目标，验证 Agent 领取同一消息时补齐约定、实际交付、用户确认和数据库来源一致。

## 自动评测在日常界面中的可见性

复用 Selection 的 trial 关联辨识后台副本，不新增实体或访问权限。自动独立审核的评测频道、成员和逐案待办不进入普通频道目录、团队成员目录、全局任务与日常 Inbox；它们仍可从原成员的具体改进提案展开证据。需要人工介入时由原 Agent 在原频道报告具体问题。历史手动评测保留原可见性；直接打开已授权记录继续遵守原 membership 校验。用量和预算账本完整保留，不能因入口隐藏而漏算成本。

## 返工继续原团队的执行上下文

真实 E2E 发现原 AgentNotifier.NotifyRejected 把任务退回发到 owner 私聊并触发消息 Run，导致团队采用的 Revision 未参与后续执行。修复共享退回/重新打开路径，复用 TriggerAgentForTask → agent_pending_work → Inbox → 原 Task 线程运行；补充退回原因并在领取时读取当前任务与当前获准团队快照。人类负责人不唤醒 Agent；Selection 内部试验继续由原 Selection 调度器按尝试上限处理，不能另排一次执行。

不新增页面、队列、表或权限；原 Task、Submission、Review 和工作所有权保留。已有完成 Run 不变，未执行返工经现有持久队列恢复。兼容旧任务的退回和重新打开入口；验收、关闭通知仍保留原行为。真实数据库回归检查原频道/线程、Task 主关联、重复通知幂等和团队版本绑定，随后重新执行完整 UI→审核退回→真实 Runtime→数据库交付链路。

## 只读交付成本随重新读取更新

交付成本的观察、用量结算可以变化而 Task.version 不变。原组件只以 task.id/task.version 重建，造成点击“重新读取”后成本仍旧。继续复用原交付弹窗 load 作为刷新边界，每次成功加载任务、提交和等待后更新只读成本组件的挂载序号，让成本重新请求原 metrics API；不改变表、权限、任务版本或审核输入语义。指标请求失败仍在成本区显示错误。现有真实 UI/API/PostgreSQL 检查补充“同一弹窗内写入兼容观察后重新读取”的断言，再重跑原手动评测链路。

未填写人工投入的任务直接显示“未记录”，避免把缺失观察展示成 0 分钟；已有人工观察仍显示实际合计。复用现有记录判定，不补写推测值。

## 英文工作区标题栏防遮挡

真实 Thinking 回归在 1280 像素窗口发现右侧频道工作区四个英文页签超出分配宽度，被全屏按钮遮挡。根因是共用标题栏固定高度、页签行不换行。只在 ChannelView 的共用标题栏允许页签自然换行，标题栏随内容增高，右侧全屏/收起按钮保留独立空间；不改全局 TabBar、路由、Thinking 领域、Session 或存储。原四视图共享修正，窄屏仍沿用原移动布局。真实无 Agent UI 场景补充 1280 与 1024 英文窗口中自动任务/Thinking 页签的原生点击，再复跑完整 Thinking Runtime 链路。

## MR 构建兼容性核对

提交前完整 `go vet ./...` 发现现有 Skill 快照安全写入依赖 `os.Root`，其中 MkdirAll、ReadFile、WriteFile、Readlink、RemoveAll、Rename、Symlink 直到 Go 1.25 才提供，而 go.mod、CI、发布和 Docker 仍声明 Go 1.22。本地验收实际使用 Go 1.26.3，因此此前产品 E2E 通过不能证明旧构建工具链兼容。

修复统一最低 Go 版本为 1.25，并同步 CI、Release、Docker 与开发文档；保留原先限制文件访问范围的标准库实现，不增加自制路径安全层或依赖。领域、API、数据库、前端状态、运行中 Session 和恢复语义均不变。验证使用最低 Go 1.25 工具链运行 vet、测试及 Linux 构建；原产品 E2E 证据仍按其实际运行环境保留。

完整 Go 测试还发现当前开发库存在仓库迁移中没有的 `agents_active_home_channel` 约束，导致主线历史 Agent 测试在构造数据时失败。为区分环境偏差与产品缺陷，MR 全量回归使用独立空 PostgreSQL 数据库、实际应用仓库所有迁移，再运行原有测试并清理仅该测试库；不删除开发库约束，不改弱历史兼容测试。
