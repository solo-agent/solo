# 交付可靠性修复与验收

目标：修复首轮已复现问题，使用完整题集和真实工作流验证 100% 通过。原始失败永不覆盖；一次全通过只描述该轮观测，不保证随机模型永不失败。

## 实施前架构

- 领域与归属：沿用 Task、不可变 Submission、Review、Run、Session 和原任务线程。任务作者提交文件，指定审核者检查该版本，用户保留原有决策权。评测只操作自己的账号和资源。
- 生命周期：作者执行 → CLI 将实际文件序列化为证据 → 原提交 API 持久化 → 原审核队列派发 → 审核者从不可变提交导出文件并验证 → 原审核 API 记录结果 → 原线程反馈 → Run 正常结束。缺失证据和错误目标不能被算作成功。
- 已追踪调用链：前端 task-delivery-dialog/use-tasks → handler/task → service/task_delivery、task_review_dispatch、agent → durable Inbox/Run → daemon ProxyRequest/ExecutingCredential → 本地 provider Session → solo CLI → 原 API/PostgreSQL → WebSocket 与前端成果弹窗。
- 当前已证实缺口：审核派发缺少当前 target 头；复用 Session 中存在旧介绍线程。文件与 SHA 的手工复制会改变换行或产生错误哈希。现有验证器检查了引用和声明，不能代替审核者实际运行检查。介绍阶段超时原因仍需从真实 Runtime 轨迹定位。
- 数据流与 API：先补齐审核派发的明确回复目标；在 CLI 增加实际文件提交和精确版本证据导出，复用 get/submissions/submit，不增加服务器端文件读取接口。提交仍由服务器验证版本、权限、证据和幂等键。工具不求解、不访问隐藏测试。
- 文件边界：只读取调用者工作目录内的普通 UTF-8 文件，遵守服务端证据大小限制；导出仅写调用者显式指定的新文件，避免覆盖与符号链接。逐字保留换行，SHA 由程序计算或验证。URI-only 证据不能冒充已导出的内联文件。
- 持久化：继续使用现有 PostgreSQL 数据结构、不可变提交与证据，无新增数据库或持久化队列。派发消息头从当前 Task/线程生成，不从 Session 历史推测。
- 前端状态：沿用成果弹窗、任务状态和原线程，无新用户入口。真实 E2E 检查源文件、证据、版本、审核原因、可见结果和数据库状态。
- 审核：先读公开规格与不可变源码，程序校验哈希，逐项运行检查；拒绝必须有实际反例，修订不得凭审核者错误理解覆盖规格。通用审核指导在产品运行上下文内修复，不注入题目答案。
- 恢复：文件导出或校验失败时返回具体错误；不接受空材料。提交/审核沿用幂等规则，原任务中返工。Runtime 超时保留事件和实际用量，原因未证实前不提高分数或把缺失记零。
- 迁移与兼容：保留旧 CLI JSON 形式、human/agent/code Gate 权限、普通频道/DM/Thinking 路由、可授权的外部 URI 证据。新增文件快捷方式只用于文件型交付，不把 Git commit 版本错误替换为文件 SHA。无需迁移生产数据。
- 运行环境：在当前 3770 checkout 配置并通过仓库根 make rebuild 管理修复版栈；切换前通过原 a8d8 仓库 make stop 停止其服务。测试始终复用 make 管理栈，完成后恢复普通 Computer。

## 验收顺序与成功条件

### 第二轮补发结果的恢复设计

首轮定向 CSV 单成员试验 `bc3398e8-d196-46dc-86dc-6a5a9bc6599c` 的代码 4/4 通过、证据和成果落库，但 Run 因 `missing_visible_result` 失败。真实轨迹显示首次只提交未发消息；公共 `result_reminder` 丢失当前 target，补发到了频道。修复位于前端状态所依赖的公共 Run 恢复路径：从当前 Run 的 channel/thread/Thinking 归属和 PostgreSQL Thread 根消息生成明确地址，再交给原 Daemon/Runtime 执行。保留原 Run、一次提醒上限、用量累计、持久化与 `HasVisibleMessage` 校验；无法解析目标则保留失败，不猜地址。频道、DM、线程及 Thinking 共用该路径，Thinking 身份继续由原运行凭据绑定。无 API、数据库或前端迁移。真实 PostgreSQL 检查目标归属，另用真实 Agent 故意在首次提交后省略消息，验证补发在原线程可见、Run 正常结束且用量完整。

1. 保存可复现的旧线程、文件换行/哈希、审核误判和启动超时证据；编写会在原行为失败的最小检查。
2. 真实文件和 PostgreSQL 检查；针对失败类别跑真实前端/API/数据库/本地 Runtime 小批次。新失败改变下一步修复，不用重复抽取最好结果。
3. 明确相对路径题的连续斜杠要求，保持原 oracle 不变并建立新数据版本。旧结果与歧义说明保留，不能在原实验中改题。
4. 冻结修复版本，执行完整 60 次开发对照、真实学习任务、60 次验收对照、20 个固定 HumanEval 及全部 5 组工作流回归。已见题只作为回归，不能声称新的未见进化收益。
5. 100% 要求该轮全部预定试验完整结束、严格交付与独立判卷均通过，工作流无失败/跳过，UI 与持久化一致，用量和资源清理完整。未达到时继续定位修复，保留每次失败；不通过降低断言、换题、排除 Team 或扩大预算掩盖问题。

### 实际模型归因补充设计

第二轮响应轨迹实际标记 `MiniMax-M3`，原报告的 `claude / sonnet` 只是 Runtime 与请求别名。沿原前端评测 → API → Daemon → Session → Claude Code 路径核对：Daemon 继承模型路由环境，公共环境合并过滤父进程 `CLAUDE_CODE_*`，因此不能从父进程的 `max` 推断实际思考强度。新归因仅在内部评测完成后只读查询已有 Run/Session 的时间与 `transcript_path`，读取该 Run 时间范围内的响应型号，过滤运行器合成消息；不读写模型设置，不保存消息内容或密钥。复用 PostgreSQL 与 Runtime 已保存的关联，不增加产品接口、表、前端入口或运行时状态。归因作为独立 JSON 证据和报告字段持久化，保留请求别名与供应商响应标识的区别；轨迹缺失、无法解析或尚不支持的 Runtime 均明确记为未核实，不影响原始通过/失败分数。旧报告不回写，只增加补充审计。模型内部权重和供应商实际思考强度仍不可由这些记录证明。验证使用本轮真实 Run、Session 和本地轨迹，并校验报告不会把请求别名回退为实际型号。

当前状态：两批交付修复已实现，真实文件、PostgreSQL、Docker 判卷与静态检查通过。第二轮真实交付及强制漏发结果恢复已经核对页面、文件 SHA、数据库与完整 Run；定向模型回归出现响应等待超时，保留失败与未知总用量。完整模型回归尚未完成，不能宣称 100%。证据保存在 `evals/results/reliability-20260912/`。

### 团队工作流的字面标记说明

第二轮团队工作流停在英文 `green` 的精确匹配：真实回复使用绿色圆点，七条纠正均已消费、消息拦截和后续请求的串行运行均由 PostgreSQL 核实；后续责任处理与撤回步骤尚未执行，整组仍记失败。补充验证只将测试发送的颜色要求明确为 ASCII 字面词，与原断言对齐。沿原消息 API → Inbox/Run → Runtime → 原线程回复 → UI/数据库检查，不改产品路径、数据模型、持久化、接口、恢复或迁移；原断言、240 秒等待、七条补充、工具与模型设置保持不变。使用新账号和独立结果目录重跑整组，保留原失败，不能用局部已通过的状态代替整组通过。

第三轮页面断言通过后的审计发现，测试在 `OBLIGATION_RESOLVED` 可见约 1 秒后撤回权限和清理成员，最后一个 Run 被取消且用量为空。补齐测试时序：沿用交付工作流已有的 PostgreSQL 检查，在权限撤回前等待本组全部 Run 正常结束且用量落库，并附加真实 Run 记录，再验证撤回与清理。使用既有等待上限和整组超时，不改产品的权限撤回语义；原第三轮仍记“断言通过、事后审计失败”。

### 从公开规格独立推导验证预期

第二轮文件内容与 SHA 均正确传递，但两位作者及独立审核者都漏掉了规格要求保留的字符；审核者的实际测试把同样的错误写进预期值。这属于 Agent 求解与验证方法的缺口，不能通过改传输、判卷器或手工修评测产物解决。修复假设是在所有 Task 作者与审核者共用的指导中明确：先从公开要求写下独立预期及边界，再运行实现；文本变换用保留/移除片段的无损重建检查，精确格式使用转义输出和严格相等，保留真实失败与推导依据。该方法没有题目名、隐藏输入或参考答案，效果必须用新一轮完整定向对照再验证。

所有权和生命周期继续沿原前端 contract → service Task 派发/审核派发 → durable Run/Session → Daemon `BuildSystemPrompt` → 本地 Runtime → CLI 提交/审核 → PostgreSQL → 原成果页面。复用一份公共验证指导，覆盖新 Session 和复用 Session 的本轮任务；使用原 evidence 保存验证命令及实际输入、预期和结果，不新增字段、表、API、UI 状态或用户入口。未通过仍在原 Task 返工，无法验证保留失败；不替换指定 reviewer、Gate、预算或等待/恢复规则。无需迁移；代码 Gate 仍执行用户预配置的真实检查，已有外部验证器继续复用。先检查指导在公共提示与派发中的接入，再使用真实栈执行相同 5 题×2 策略；只有严格 10/10 且证据和用量完整，才进入原定完整 141 次与五组工作流验收。
